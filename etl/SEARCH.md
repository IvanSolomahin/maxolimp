# Поиск по олимпиадным задачам

Поиск работает в **той же SQLite-базе**, что и исходные задачи: `olimpiads_data_v2/olimpiads.sqlite3`. Таблица `problems` сохраняет все исходные поля. В эту базу добавлены FTS5-индекс и таблицы векторов. Отдельная поисковая SQLite-база больше не используется.

## Векторизация

По умолчанию используется `qwen/qwen3-embedding-4b` через [OpenRouter Embeddings API](https://openrouter.ai/docs/api/api-reference/embeddings/create-embeddings). На одну задачу приходится максимум два входных текста:

| Вид вектора | Подготовка текста | Назначение |
| --- | --- | --- |
| `topic` | `classifier.strip()`, затем перевод строки и `statement.strip()`; пустые части опускаются | Поиск по условию и теме |
| `solution` | `solution.strip()` целиком | Поиск по способу решения |

Ответ (`answer`) в вектор не входит; решения не разбиваются на чанки. Пустое поле не векторизуется. Длина каждого текста до отправки проверяется [токенизатором Qwen3-Embedding-4B](https://huggingface.co/Qwen/Qwen3-Embedding-4B/blob/main/tokenizer.json). Лимит в конфигурации — 32 768 токенов на текст. Превышающий лимит текст не обрезается: запись попадает в `search_skipped`, а задача остаётся доступна через другой вектор и FTS5.

Непустые тексты отправляются в `POST /api/v1/embeddings` массивом `input`, по умолчанию до 32 текстов в запросе. Ответ проверяется по числу и индексам векторов, размерности и конечности значений. Для Qwen ожидается 2 560 чисел; в SQLite они сохраняются как little-endian `float32`, по 10 240 байт на вектор. Документы и запросы векторизуются одной моделью, без параметра `input_type`.

## Схема единой базы

| Объект | Что хранит |
| --- | --- |
| `problems` | Все исходные задачи и поля: предмет, ID, олимпиада, класс, год, тур, условие, тип, классификатор, решение, ответ, URL, время сбора |
| `problem_fts` | FTS5 по `classifier`, `statement` и `solution`; внешний источник текста — `problems` |
| `search_vectors` | `model`, `dimensions`, `subject`, `problem_id`, `kind`, SHA-256 текста и бинарный вектор |
| `search_skipped` | Тексты, превышающие лимит, с числом токенов и причиной |
| `search_meta` | Версия поисковой схемы |

`problem_fts` связан с `problems` через SQLite `rowid`. Триггеры на вставку, изменение и удаление задачи обновляют FTS5 автоматически, в том числе при работе парсера. Векторы не пересчитываются триггерами: после изменения текстов выполните повторное индексирование. Ключ в `search_vectors` включает ID модели и размерность, поэтому в одной базе могут сосуществовать индексы нескольких моделей без смешивания векторов.

## Файлы, ключ и резервные копии

Рабочая база — `olimpiads_data_v2/olimpiads.sqlite3`. Токенизатор кэшируется в `olimpiads_data_v2/search_indexes/qwen3-embedding-4b-tokenizer.json`; это **не** база данных. Ключ можно хранить в переменной `OPENROUTER_API_KEY` или в `olimpiads_data_v2/openrouter.key` с правами `600`. Весь каталог `olimpiads_data_v2/` исключён из Git, включая базу, ключ, токенизатор и локальные резервные копии. Публикация кода в Git не переносит сами задачи и векторы на другую машину.

Теперь единая база содержит и исходные задачи, и векторы, поэтому её стоит резервировать целиком. Для согласованной копии работающей SQLite-базы используйте SQLite Backup API; не копируйте только основной `.sqlite3`-файл во время записи. Локальные копии: `olimpiads_data_v2/olimpiads.before-unified.sqlite3` — исходная база **без векторов** до переноса; `olimpiads_data_v2/olimpiads.unified-backup.sqlite3` — полная база **с векторами** после переноса. Старый отдельный индекс после проверки был удалён.

## Индексирование и обновления

```bash
python3 -m pip install -r requirements.txt
./run_search_index.sh
```

Скрипт использует 8 воркеров и пакеты по 32 текста. В терминале отображаются задачи, процент, новые векторы, токены, активные запросы, повторы и примерное оставшееся время. Прерванный запуск можно повторить: SHA-256 подготовленных текстов позволяет пропустить неизменённые векторы и восстановить отсутствующие. Изменение условия или классификатора пересчитывает только `topic`; изменение решения — только `solution`. Изменение других исходных полей векторизации не требует. Полный запуск также удаляет устаревшие векторы задач, исчезнувших из `problems` или ставших пустыми.

`--workers` задаёт верхнюю границу одновременных запросов. Код начинает максимум с восьми, повышает параллельность после успешных ответов и снижает её при временных сетевых ошибках. Сетевые разрывы и ответы 429/5xx повторяются с паузой до восьми попыток. Не запускайте два процесса индексирования одной базы одновременно: SQLite допускает одного писателя.

Для другой модели задайте `--model`, `--dimensions`, `--max-tokens` и её токенизатор через `--tokenizer` или `--tokenizer-url`. Первое использование модели требует построить её векторы. Возврат к ранее использованной модели использует сохранённые записи `search_vectors`. Параметр `--index-dir` оставлен для совместимости: он задаёт каталог кэша токенизатора и путь поиска старого отдельного индекса при миграции, но больше не выбирает рабочую SQLite-базу.

Для перехода со старой схемы предусмотрена одноразовая команда `task_search.py migrate`. Она сверяет хеши с `problems` и копирует векторы из прежнего файла без OpenRouter. На этой базе перенос уже выполнен; повторно запускать команду не требуется.

## Поиск

```python
from task_search import Config, search

results = search(
    "закон сохранения импульса",
    mode="topic",      # topic, solution или both
    method="hybrid",   # fts, vector или hybrid
    subject="physics", # math или physics
    grade="9", year="2016", k=5,
    config=Config(),
)
```

Для `vector` и `hybrid` нужен ключ OpenRouter; `fts` работает без сети и ключа. В CLI общие параметры ставятся перед командой:

```bash
.venv/bin/python task_search.py --api-key-file olimpiads_data_v2/openrouter.key search \
  'закон сохранения импульса' --mode topic --method hybrid --subject physics -k 5
```

FTS5 разбивает запрос на слова и ранжирует совпадения через `bm25`. Для режима `topic` оно ищет в классификаторе и условии, для `solution` — в решении. Векторный поиск создаёт вектор запроса той же моделью и считает косинусное сходство. Режим `both` использует оба вида векторов. Метод `hybrid` складывает вклады рангов FTS5 и векторов по формуле `1 / (60 + rank)`. Фильтры по предмету, классу и году применяются до ранжирования; диапазон класса `8-9` подходит для `--grade 8` и `--grade 9`.

Точные повторы непустого условия внутри одного предмета объединяются: остальные ID указаны в `duplicates` с учётом фильтров. Это сравнение текста после `strip()`, а не смысловое объединение. Длинное решение без вектора ищется через FTS5, а задача — по вектору условия.

Векторный поиск перебирает подходящие записи `search_vectors` и пока не использует ANN. Задержка растёт с числом векторов и зависит от фильтров, диска и OpenRouter. На одном запросе к единой базе по физике наблюдалось 0,30 с для `fts` и 6,3 с для `hybrid` с сетевым вызовом; это пример, не гарантия времени ответа.

## Проверки качества и скорости

`search_labels.json` содержит стартовые размеченные запросы по обоим предметам и режимам. `evaluate_search.py` сравнивает `fts`, `vector` и `hybrid` по Recall@k и MRR@k:

```bash
.venv/bin/python evaluate_search.py search_labels.json \
  --api-key-file olimpiads_data_v2/openrouter.key -k 10
```

Восемь стартовых запросов подходят для проверки работоспособности; для вывода о качестве на всей коллекции нужна более широкая разметка. Пакеты 8, 16, 32, 64 и 128 сравнивались на одинаковых 256 текстах при восьми воркерах и двух проходах. В этой пробе пакет 32 был самым быстрым:

| Текстов в запросе | Время, проход 1 / 2 | Средняя скорость, векторов/с |
| ---: | ---: | ---: |
| 8 | 30,94 / 30,57 с | 8,32 |
| 16 | 11,77 / 14,35 с | 19,80 |
| **32** | **7,02 / 14,96 с** | **26,80** |
| 64 | 14,84 / 11,93 с | 19,36 |
| 128 | 19,86 / 15,45 с | 14,73 |

Повторить замер можно командой `.venv/bin/python benchmark_batch_sizes.py`, когда основной индекс не работает. По локальному токенизатору все 39 235 непустых входных текстов содержали около 19,66 млн токенов; стоимость зависит от действующей цены OpenRouter и фактического `usage` в ответах API.
